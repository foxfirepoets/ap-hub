## Findings

1. **LOW (confidence 0.6) — `Math.abs()` clock-skew tolerance in the CSRF state token's expiry check** (`src/auth/connect-state.ts:58`). Accepts a timestamp up to 5 minutes in the future in addition to the past, extending the theoretical validity window to ~10 minutes. **STATUS: EVALUATED, LEFT AS-IS.** This is a deliberate tradeoff, not an oversight: the signer and verifier are two separate OS processes (by design — see the spec's rejected alternative of merging them, §17) that can have ordinary clock drift; tightening this would risk rejecting legitimate connections over a non-exploitable window the HMAC signature already protects (timestamp forgery is impossible without the signing key regardless of direction). Confidence 0.6, no exploit path identified.
2. **LOW (confidence 0.6) — `SESSION_COOKIE_SECRET` defaults to an empty string if unset** (`src/config.ts`, pre-existing). This feature adds a second consumer (state-token signing) of an already-shared secret. **STATUS: OUT OF SCOPE, NOT TOUCHED.** Predates this feature (CHUNK_1_AUTH); this diff makes zero changes to `src/config.ts`'s handling of this variable. Flagged as a standing operational recommendation for the repo, not a defect introduced here.

**No CRITICAL, HIGH, or MEDIUM findings.**

## Overall result: PASS
The independent adversarial review targeted exactly the properties that matter for a real OAuth integration — CSRF token forgeability, verification ordering relative to the token exchange, tenant-id provenance, open-redirect surface, secret exposure, and the automation-safety guarantee (`automation_level` never silently changed) — and found all of them correctly implemented, each backed by an explicit adversarial unit/integration test (tampered token, expired token, cross-secret rejection, tenant-smuggling attempt, embedded open-redirect attempt). Gate **212/212** green throughout; `test/onboarding.test.ts` (11 tests, backend/action layer) re-verified unmodified and green after the final chunk; `web:build` 27 routes (25 baseline + exactly the 2 new routes this feature adds); all six guarantee-bearing files (`src/qbo/write.ts`, `src/gatekeeper/forwarder.ts`, `src/pipeline/**`, `migrations/**`) confirmed byte-for-byte unchanged across all 5 chunks, and the four pre-existing OAuth-exchange functions (`exchangeGmailCode`, `exchangeQboCode`, `assertExpectedCompany`, `saveToken`) confirmed unchanged at the function-body level — this feature only changed what happens to the HTTP response around them.

**Worth naming explicitly:** the pre-existing code this feature replaced contained a real, exploitable IDOR — an unsigned `state=<tenantId>` query parameter trusted directly as the connecting tenant's identity on both OAuth callbacks, meaning any caller could forge a different tenant id and connect their own Gmail/QBO account to someone else's ap-hub tenant. This was never previously flagged by any audit in this repo's history. CHUNK_1/CHUNK_2 of this feature close it as a structural consequence of adding the signed CSRF state token, not as a targeted fix — this build made the system meaningfully more secure, not merely no-worse.

**Verified safe (independent fresh-context review, cited with file:line):** constant-time signature comparison with a safe length pre-check (`connect-state.ts:46-48`); malformed-token rejection before any crypto/parsing work (`connect-state.ts:41`); state verified and checked before any exchange call on every path in both callbacks (`gmail-oauth.ts:39-44`, `qbo-oauth.ts:61-66`); tenantId sourced only from the resolved session, with an explicit smuggling test (`connections.ts:16-19`, `connections-start.test.ts:98-112`); redirect target always server-constructed, `reason` never reflects raw input (`gmail-oauth.ts`/`qbo-oauth.ts` redirect calls, `onboardingErrors.ts:44-55`); no client-secret exposure (`connect-urls.ts:14-27`); `automation_level` untouched by the automatic walk (`page.tsx` `goStep` call sites, `onboarding.ts`'s `COALESCE`); no XSS in any new/modified component; QBO wrong-company classification has no meaningful bypass; the returning-owner auto-walk is provably idempotent and structurally cannot reach `post_sandbox`.

**Residual risks (undetectable without live execution / real transcript — this is the load-bearing caveat for this audit):**
1. **No live Google/Intuit OAuth round-trip was executed anywhere in this session.** This sandbox has no real provider test credentials. Every property inside this repo's control (signing, verification, ordering, redirect construction, session/tenant resolution, DB persistence, idempotency) was verified by direct code review and targeted tests against realistic mocks — but the actual shape of Google's and Intuit's real callback responses (exact `error=` values, token response field names) has never been exercised against the live APIs. A human must complete one real click-through of each provider's consent screen in an environment with real sandbox credentials before this feature is genuinely launch-ready — this is an operational verification step the code-level gate cannot substitute for, and it is not optional.
2. The `Math.abs()` clock-tolerance design (finding #1) assumes the two processes' clocks stay within roughly ±5 minutes of each other; a production deployment with severe, sustained clock drift between the pipeline server and the Next.js app would see connect attempts fail with `invalid_state` (a safe failure mode — never a security failure — but worth knowing operationally).
3. `SESSION_COOKIE_SECRET`'s empty-string default (finding #2) means a misconfigured production deployment that never set this variable would have forgeable session cookies AND forgeable connect-state tokens simultaneously — a standing, pre-existing operational risk this feature inherits but does not introduce or worsen materially (it was already single-point-of-failure for session security before this diff).
