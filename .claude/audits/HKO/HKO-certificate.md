## Findings (initial verdict: FAIL — 1 HIGH)

1. **HIGH — automatic pipeline bypasses DRY_RUN_LOCKED** (`src/pipeline/mapping.ts:248-263` `proposeHandler`/`enqueuePost` → `post_sandbox` job → pre-fix `postSandboxHandler`, zero awareness of `onboarding_state`). `assertNotDryRunLocked` was wired only into `approveProposal` (`src/services/approve.ts:98`) and `retryProposal` (`src/services/proposals.ts:64`) — both human-triggered. A tenant mid-onboarding, or freshly created via the new `bootstrap-tenant` CLI, whose extraction crossed `AUTO_THRESHOLD` (default 0.9) would still be auto-posted to the QBO sandbox by the pre-existing pipeline — contradicting the onboarding UI's explicit promise ("Posting is locked until you pick anything other than Off", `app/(app)/onboarding/page.tsx:314-315`) and the code's own doc comment. **STATUS: FIXED** — `src/pipeline/register.ts` now exports `guardedPostSandboxHandler`, which checks `isDryRunLocked` before delegating to the real handler; every `post_sandbox` job (manual or automatic) already funnels through this one registration. `src/pipeline/mapping.ts` and `src/pipeline/posting.ts` remain byte-for-byte unchanged. New tests prove: locked → 0 postings + `dry_run_locked` exception row; unlocked (explicit `automation_level`, or no `onboarding_state` row at all — pre-CHUNK_6/backward-compat) → posts exactly as before.
2. **MEDIUM — CSV formula injection in the reviewer-dashboard export** (`scripts/build-review-dashboard.mjs` `csvEscape`, CWE-1236). Vendor/finding/source text originates from AP email content (attacker-influenced) and was written unescaped into the exported CSV; a crafted vendor name (`=cmd|'/C calc'!A0`) could execute as a formula when opened in Excel/Sheets. **STATUS: FIXED** — leading `=`,`+`,`@`,tab,CR, or `-` now gets a neutralizing `'` prefix. A first-attempt fix placed `-` mid-character-class, which JS regex resolves as the range `[+-@]` (charcodes 43-64) — silently over-matching every digit and corrupting numeric CSV columns; caught by executing the actual regex in Node before commit, not just by grepping for its presence.
3. **LOW — `isDryRunLocked` treats "no `onboarding_state` row" as unlocked** (`src/services/onboarding.ts:215-223`), by original design, to preserve backward compatibility for tenants/tests that predate CHUNK_6. Combined with the new `bootstrap-tenant` CLI, a freshly bootstrapped tenant is unlocked from creation until someone starts onboarding. The HIGH fix above closes the actual posting risk regardless of this row's presence (the guard now runs on every `post_sandbox` job); this is a residual design note, not a live gap. **STATUS: NOT CHANGED** — deliberately left as-is (already tested, already disclosed as a design tradeoff); noted as a residual risk below rather than fixed, since the security reviewer flagged it as optional/low-priority once the HIGH fix lands.

## Overall result: PASS (post-remediation)
Initial audit was **FAIL** (1 HIGH). Both the HIGH and the disclosed MEDIUM finding were remediated and re-validated in-session: gate **183/183** green (was 179 before this audit's fixes; started this session's build at 129), lint + typecheck clean, `web:build` compiled (25 routes, unchanged by these fixes), six-guarantee suite green, `src/qbo/write.ts` / `src/gatekeeper/forwarder.ts` / `src/pipeline/mapping.ts` / `src/pipeline/posting.ts` byte-for-byte UNCHANGED vs `9de30fc` (and vs the original `9858eaa` base across the whole CHUNK_6-8 build).

**Verified safe (independent fresh-context review, cited with file:line):** SQL injection — none, every new query in `provisioning.ts`/`review/snapshot.ts`/`review/apply-decisions.ts`/`onboarding.ts`/`digest.ts`/`notifications.ts` parameterized; tenant scoping — every tenant-data query goes through `scopedQuery`, which throws if unscoped; `bootstrapTenant` — CLI-only, zero references from any `app/api/**` route; XSS in the offline dashboard — `<` truly escaped to `<` in the embedded `DATA`, all rendering via `textContent`/`createTextNode`, zero `innerHTML`/`eval`/`Function()` in the generator; replay CLI — imports only `approveProposal`/`rejectProposal`, never touches `write.ts` or `postings` directly, every decision id resolved under the caller's tenant before acting; resource leaks — `withTransaction` releases its client in a `finally` on every path; redaction — `redact()` does real key- and regex-based work and is applied to the full review snapshot before it's written to disk; `onboard` permission — server-enforced via `ensurePermission`, not just a client-side UX check; no hardcoded tenant-specific values found in the new dashboard/digest/onboarding code.

**Residual risks (undetectable without live execution / real transcript):**
1. Real Google SSO end-to-end (token exchange, cookie behavior across a real browser redirect) is still not exercised by the DB-backed tests — unchanged from the prior audit, verify against a live Google client before production.
2. `isDryRunLocked`'s "no row = unlocked" default (LOW finding #3 above) means a freshly bootstrapped tenant that never starts onboarding is unlocked by default. The HIGH fix means this can no longer result in an unauthorized post while a *known* onboarding is in progress, but a tenant that skips onboarding entirely still relies on the pre-existing pipeline's own confidence/threshold/proof gates rather than an explicit onboarding lock. Consider defaulting `bootstrapTenant` to create a locked `onboarding_state` row if a future audit wants this closed further.
3. The reviewer-dashboard CSV/JSON export is a local file that may be emailed or shared outside the system once a reviewer downloads it — no distribution control exists (by design, per the spec's "offline artifact" requirement), so operators should be aware exported decision files carry real financial data.
4. `app/` route handlers (including the new onboarding wizard and notifications panel) are covered by `web:build` typecheck + Vitest at the service/action layer, not a Playwright E2E — CHUNK_5's happy-path E2E was not extended to cover onboarding or notifications UI flows.
